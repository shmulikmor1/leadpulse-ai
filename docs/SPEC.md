# LeadPulse AI – מסמך אפיון

גרסה 0.2 · 13.10.2026 · סטטוס: מאושר, בפיתוח

## 1. מה בונים

סוכן AI שמקבל פנייה גולמית של לקוח לעסק (הודעת וואטסאפ, טופס "צור קשר", מייל) ומחזיר תוך שניות:

- מה הלקוח רוצה (כוונה וקטגוריה)
- כמה זה דחוף, בציון 1–5, עם נימוק
- סיכום של שורה אחת לבעל העסק
- פרטים שחולצו מהטקסט (שם, טלפון, מוצר, תקציב, מועד)
- תשובה מוצעת ללקוח, מוכנה לשליחה
- הפעולה הבאה המומלצת

כל ניתוח נשלח גם ל-webhook של Make, כך שליד דחוף יכול להפעיל התראה אוטומטית.

## 2. למי זה מיועד

בעל עסק קטן שמקבל עשרות פניות ביום ולא מספיק לענות לכולן בזמן. הוא מפסיד לידים חמים כי הם נקברים בין שאלות כלליות. LeadPulse ממיין בשבילו ומכין את התשובה.

## 3. היקף

**בפנים (PoC):**

- עמוד אחד בעברית (RTL): הזנת פנייה, דוגמאות מוכנות, הצגת תוצאה
- היסטוריית ניתוחים של הסשן הנוכחי, ממוינת לפי דחיפות
- פונקציית שרת אחת שמדברת עם ה-LLM ומחזירה JSON מאומת
- שליחת התוצאה ל-webhook של Make, וקובץ blueprint מוכן לייבוא
- פריסה ב-Vercel, ריפו ציבורי עם README

**בחוץ (במכוון):**

- משתמשים, התחברות והרשאות
- בסיס נתונים ושמירה לאורך זמן
- חיבור אמיתי לוואטסאפ או למייל נכנס
- שליחה אוטומטית של התשובה ללקוח
- ריבוי עסקים והגדרות לכל עסק

הסעיפים שבחוץ הם הצעדים הטבעיים להפיכת ה-PoC למוצר, והם יופיעו ב-README כ"המשך הדרך".

## 4. זרימה

1. המשתמש מקליד פנייה או בוחר דוגמה, ולוחץ "נתח".
2. הדפדפן שולח `POST /api/analyze-lead`.
3. השרת בודק את הקלט (אורך, קצב בקשות) ושולח ל-LLM פרומפט עם דרישה ל-JSON במבנה קבוע.
4. השרת מאמת את תשובת המודל מול הסכמה. אם היא לא תקינה, הוא מנסה פעם נוספת, ואחר כך מחזיר שגיאה ברורה.
5. אם מוגדר `AUTOMATION_WEBHOOK_URL`, השרת שולח אליו את התוצאה. כישלון בשליחה לא מפיל את הבקשה.
6. הדפדפן מציג את התוצאה ומוסיף אותה להיסטוריה.

## 5. ארכיטקטורה

## 6. חוזה ה-API

**בקשה** – `POST /api/analyze-lead`

```json
{ "message": "היי, המזגן שלי נוזל כבר יומיים, אפשר טכנאי היום? דני 050-1234567" }
```

**תשובה** – `200`

```json
{
  "intent": "בקשת שירות דחופה – תיקון מזגן",
  "category": "service",
  "urgency": 5,
  "urgencyReason": "תקלה פעילה, מבקש טיפול היום",
  "summary": "דני מבקש טכנאי היום לנזילה במזגן שנמשכת יומיים",
  "extracted": { "name": "דני", "phone": "050-1234567", "product": "מזגן", "budget": null, "timeframe": "היום" },
  "suggestedReply": "היי דני, קיבלנו את הפנייה ...",
  "nextAction": "להתקשר ללקוח בשעה הקרובה ולתאם טכנאי"
}
```

`category` הוא אחד מ: `sales`, `service`, `support`, `complaint`, `info`, `spam`.

**שגיאות:** `400` קלט חסר או ארוך מ-2,000 תווים · `429` יותר מדי בקשות · `502` המודל לא החזיר תשובה תקינה.

## 7. ממשק

- **אזור הזנה:** תיבת טקסט, 4–5 כפתורי דוגמה (ליד חם, תלונה, שאלה כללית, ספאם, פנייה מעורפלת), כפתור "נתח".
- **כרטיס תוצאה:** מד דחיפות צבעוני, תגית קטגוריה, סיכום, פרטים שחולצו, התשובה המוצעת עם כפתור העתקה, והפעולה הבאה.
- **היסטוריה:** רשימת הניתוחים מהסשן, הדחופים למעלה.
- **מצבים:** טעינה, שגיאה עם הסבר, ומצב ריק שמזמין לנסות דוגמה.
- העיצוב צריך להיראות כמו מוצר ולא כמו תרגיל: היררכיה ברורה, ריווח נדיב, תצוגה תקינה במובייל.

## 8. האוטומציה ב-Make

תרחיש אחד שמיובא מקובץ blueprint:

1. **Webhook** – מקבל את תוצאת הניתוח.
2. **IF** – דחיפות 4 ומעלה?
3. **כן:** התראה מיידית לבעל העסק (מייל או טלגרם) עם הסיכום והתשובה המוצעת.
4. **לא:** הוספת שורה לגיליון Google Sheets למעקב.

Make הוא שירות ענן, ולכן האוטומציה פועלת גם בדמו החי בלי שום רכיב מקומי. ה-README יסביר איך לייבא ולהפעיל.

## 9. דרישות לא-פונקציונליות

- מפתח ה-API לא מגיע לדפדפן ולא נכנס ל-git (`.env` ב-`.gitignore`, יש `.env.example`).
- הגבלת אורך קלט והגבלת קצב בסיסית לפי IP, כדי להגן על המכסה החינמית.
- הפנייה של הלקוח מוזנת למודל כנתון ולא כהוראה, כדי שטקסט כמו "התעלם מההוראות" לא ישנה את ההתנהגות.
- שום פנייה לא נשמרת בשרת.
- תשובה תוך 5 שניות ברוב המקרים.
